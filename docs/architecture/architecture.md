## 1. Пять правил, на которых держится всё остальное

1. **Числа — в `assets/data/*.json`, не в коде** (ADR-0001). Код читает их через `Tune`.
2. **Чистая логика отдельно от узлов.** Формулы, генерация, броски добычи, выбор рун — это
   классы `RefCounted` со `static func`, которые получают данные и `RandomNumberGenerator`
   параметрами (как `RoomGen.generate`). Их можно проверить тестом без сцены.
3. **«Вниз — вызовом, вверх — сигналом, вбок — через шину `Events`».** Родитель вызывает методы
   детей; ребёнок сообщает родителю сигналом; несвязанные системы (HUD, звук, экономика)
   слушают `Events`. Горячий путь удара — прямые вызовы, без шины.
4. **Весь урон по врагу идёт через `Enemy.hurt(hit)`** (ADR-0002), весь урон по герою — через
   `Player.hurt(hit)`. Других путей нет.
5. **Всё случайное в геймплее — из именованных потоков `RunRng`** с seed забега (ADR-0003).
   Глобальные `randf()`/`randi()` — только для косметики (дрожь камеры, разброс цифр урона).

## 3. Сцены и дерево узлов забега

```
/root
├─ Tune      (автозагрузка) числа из assets/data/*.json
├─ Events    (автозагрузка) шина сигналов
├─ Game      (автозагрузка) MetaState, текущий RunState, переходы между сценами
└─ Run       scenes/run/run.tscn — run.gd: держит RunState и RunRng, строит комнаты по Route
   ├─ World        Node2D, world.gd (бывший Main): hitstop, shake, rings, процесс-порядок
   │  ├─ Backdrop    параллакс-слои фона (ADR-0004)
   │  ├─ Room        room.gd: пол, стены, платформы, двери, сундуки
   │  ├─ Enemies     Node2D — все Enemy (группа "enemies")
   │  ├─ Pickups     добыча, угли
   │  ├─ Projectiles снаряды врагов и героя
   │  ├─ Player      CharacterBody2D
   │  │  ├─ Visual   PlayerVisual + риг (Skeleton2D, ADR-0005)
   │  │  └─ Camera2D zoom из Tune (ADR-0004)
   │  └─ Fx          вспышки, кольца, пыль
   ├─ Hud          CanvasLayer (слой 10)
   ├─ BoonScreen   CanvasLayer (слой 20), process_mode = ALWAYS, ставит паузу
   └─ Sfx          Node, слушает Events
```

Другие сцены: `scenes/main.tscn` (старт: меню / проверочная комната, как сейчас),
`scenes/hub/hub.tscn` (база-острог). Переход между ними делает только `Game.goto_*()`.

**Смена комнаты** не перезагружает сцену `Run`: `run.gd` удаляет детей `Room`, `Enemies`,
`Pickups`, `Projectiles` и строит новую комнату. Герой и камера остаются.

**Пауза** (экран руны, меню): `get_tree().paused = true`; экраны работают с
`process_mode = PROCESS_MODE_ALWAYS`. **Хитстоп — это не пауза**: актёры сами пропускают кадр,
пока `world.hitstop > 0` (как сейчас в `player.gd` и `dummy.gd`).

## 4. Как системы общаются

| Способ | Когда | Пример |
|---|---|---|
| **Прямой вызов** | родитель → ребёнок; горячий путь удара; чистая логика | `Run` → `room.build(layout)`; `Player` → `enemy.hurt(hit)`; `DamageRules.final(hit, view)` |
| **Сигнал узла** | ребёнок → родитель, один слушатель рядом | `Enemy.died` → `Run` (считает «комната очищена»); `Doors.chosen` → `Run` |
| **Шина `Events`** | редкие события, которые слушают далёкие системы | `enemy_killed`, `player_hurt`, `room_cleared`, `rune_taken`, `flare_fired`, `run_ended` → HUD, звук, экономика, благословения |
| **Внедрение ссылки** | системе нужен общий объект | `player.world = world`; `player.build = run_state.build`; HUD получает `RunState` при создании |

Шина — **одна** автозагрузка `src/core/events.gd`, только объявления сигналов, без логики и
без состояния. Сигналы — в прошедшем времени (`enemy_killed`, не `kill_enemy`). Новый сигнал на
шине добавляется, только если его слушает система из **другого** модуля. Шину нельзя
использовать, чтобы получить ответ (сигнал не возвращает значение) — для этого прямой вызов.

`World` — единственная точка «ощущений удара»: `world.request_hitstop(t)` (берёт большее, а
не сумму — GDD movement-and-combat §3.10), `world.add_shake(s)`, `world.add_ring(p, r)`.
Герой и враги не пишут в `world.hitstop` напрямую (сейчас пишут — исправляется в задаче 1, §9).

## 5. Данные контента

Решение — ADR-0001: **JSON в `assets/data/`, один файл на таблицу**, читает `Tune`.

```
assets/data/
├─ tuning.json     скаляры героя, камеры, комнат (есть)
├─ enemies.json    виды врагов по id: hp, урон, вес, скорость, награды
├─ bosses.json
├─ gods.json       боги, руны по слотам, союзы (DUOS)
├─ weapons.json    35 основных + 20 доп., редкость, аффиксы
├─ buffs.json
├─ economy.json    цены, улучшения Святилища, Пепел
└─ locations.json  порядок локаций, ярусы, цвета
```

Таблица — словарь `{ "<id>": { поля } }`; первым ключом идёт `"_note"` с единицами измерения.
`Tune.table("enemies")` возвращает словарь, `Tune.row("enemies", "bat")` — одну строку с
проверкой, что она есть. Godot-ресурсы `.tres` используются **только** для того, что редактор
делает лучше: сцены, анимации, тема интерфейса, материалы, шейдеры, шины звука.

## 6. Сохранение

Решение — ADR-0003. Коротко:

- Один файл `user://save.json`: `{ "version": 1, "meta": {...}, "run": null | {...} }`.
  Поля — таблица GDD economy-and-meta §3.9.
- Загрузка **сливает** файл с умолчаниями: новые поля не ломают старый сейв.
- Запись атомарная: `save.tmp` → проверка → переименование в `save.json`.
- Когда пишем: конец забега, покупка на базе, вход на привал (`haven`). **В середине комнаты
  забег не сохраняется** — как в прототипе.
- `--fresh` в аргументах запуска игнорирует сейв (аналог `?fresh=1` прототипа).

## 7. Детерминизм

- Забег получает `run_seed` (случайный при старте, либо `--seed=N` в аргументах — уже есть в
  `main.gd`).
- `RunRng` выдаёт **отдельный** `RandomNumberGenerator` на каждую цель: `rooms`, `doors`,
  `loot`, `boons`, `enemies_ai`. Seed потока = `hash([run_seed, "<имя>"])`. Комната получает
  свой генератор из `hash([run_seed, "rooms", tier, room_k])` — тогда одна и та же комната
  одинакова, даже если игрок по-разному дрался до неё.
- Состояние потоков (`rng.state`) пишется в снимок забега на привале.
- Чистая логика никогда не создаёт генератор сама — получает его параметром.
- Тест: один seed → одинаковая комната, одинаковая развилка, одинаковое предложение рун.
- Ограничение: прототип и порт с одним seed дают **разные** комнаты (разные генераторы;
  GDD room-generation §4). Сверяем порт с прототипом по правилам и диапазонам, не по seed.

## 8. Бюджеты производительности

| Бюджет | Значение | Как проверяем |
|---|---|---|
| Кадр | 60 fps, ≤ 16,6 мс на GTX 1060 / 3 ГБ (цель art bible); логика ≤ 4 мс | монитор Godot «Process» в бою с 30 врагами |
| Врагов в комнате одновременно | до 30 + до 60 снарядов | стресс-сцена в `tests/integration/` |
| 2D-источники света в кадре | до 16 (art bible §8) | профайлер, technical-artist |
| Видеопамять текстур | до 1 ГБ на загруженную локацию | монитор «Video RAM» |
| Смена комнаты | ≤ 0,3 с без видимой заминки | замер `Time.get_ticks_msec()` в `run.gd` |
| Запуск до меню | ≤ 3 с | замер |

Проверка ударов — прямоугольники (`Rect2.intersects`), как в прототипе, без `Area2D`: при 30
врагах это сотни сравнений за кадр — ничтожно мало. Физика Godot нужна только герою (пол,
платформы, стены).

## 9. Ближайшие три задачи по коду

1. **Базовый класс `Enemy` и `Hit`** (ADR-0002). `StrawDummy` наследует `Enemy`, `Player`
   перестаёт знать о чучеле. Добавить `World` (`request_hitstop`, `add_shake`) и
   `Player.hurt(hit)` с щитом и неуязвимостью. Тесты на `DamageRules`.
2. **Разрешение и камера** (ADR-0004): `project.godot` → 1920×1080, `canvas_items`, `expand`;
   `camera_zoom` в `tuning.json`; снимок экрана в `production/qa/evidence/`. Маленькая задача,
   но её надо сделать до любой работы с графикой и интерфейсом.
3. **Таблица врагов и первые 4 вида** (ADR-0001 + ADR-0002): `enemies.json`, `Tune.table/row`,
   ползун, летучая мышь, часовой (щит спереди), пузырь — по GDD enemies-and-elites §3.2.

`RunState`/сохранение (ADR-0003) и риг героя (ADR-0005) идут после: первому нужны руны и
забег (шаги 5–7 порядка переноса), второму — нарисованные части героя.
